# GitHub Actions 发布

工作流：`.github/workflows/release.yml`。在 Windows runner 上使用 JDK 17 和校验过的 Android 官方构建工具，复用本地 `build.ps1`。

## 首次配置

在仓库 Settings → Secrets and variables → Actions → New repository secret 创建：

| Secret | 内容 |
| --- | --- |
| `SIGNING_KEYSTORE_BASE64` | 含签名私钥的完整密钥库文件的单行 Base64，不是公钥证书文本 |
| `SIGNING_STORE_PASSWORD` | 密钥库密码 |
| `SIGNING_KEY_ALIAS` | 签名条目别名，本项目为 `myhook` |
| `SIGNING_KEY_PASSWORD` | 签名私钥密码 |

本地导出文件位于被 Git 忽略的 `signing/`：`myhook-release.jks`、`myhook-release.jks.base64.txt` 和 `github-secrets.json`。JSON 四个字段分别对应上述四个 Secret，复制值时不包含引号。不要把整份 JSON 放进单个 Secret。

该导出沿用原有私钥/证书，为密钥库和私钥分别设置随机密码，未替换签名身份。原 `myhook-debug.jks` 保持不变。证书 SHA-256：

```text
59d5bcb32b417c5bbb861e4b1a95f5f4ffeeb64d1dcbb49f40e531f456973084
```

工作流在签名后核对这个指纹；缺失 Secrets、密码不正确或指纹不一致都会停止发布。密钥仅写入 runner 临时目录，并在构建步骤后清理。

## 后续发版

1. 修改 `app/build.gradle.kts` 中的 `versionName` 和递增的 `versionCode`。`build.ps1` 会直接读取它们，无须另外改脚本内版本。
2. 新增对应说明，例如 `docs/releases/v0.2.1.md`。
3. 提交并推送源码，再创建版本 tag：

```sh
git tag -a v0.2.1 -m "MyHook 0.2.1"
git push origin v0.2.1
```

示例仅用于后续版本；首次发布为 `v0.2.0`。tag 必须与源码版本完全一致。包含连字符的版本会标为 prerelease。

工作流只响应 `v*` tag，不在普通分支推送时发布。也支持对已有 tag 手动运行：GitHub CLI 可执行 `gh workflow run release.yml --ref v0.2.0`。失败后应优先使用 Actions 页的 Re-run failed jobs；已发布的同名 Release 不会被自动覆盖。

发布附件为 `MyHook-<version>.apk` 和 `MyHook-<version>.apk.sha256`。`gh release create` 使用已存在的远程 tag，先上传附件再公开 Release。[GitHub CLI 文档](https://cli.github.com/manual/gh_release_create)

## 本地复现发布构建

将 `MYHOOK_STORE_PASSWORD`、`MYHOOK_KEY_PASSWORD` 设置为导出密钥对应的环境变量，再执行：

```powershell
.\build.ps1 -Release -KeyStore signing/myhook-release.jks -KeyAlias myhook -ExpectedCertificateSha256 59d5bcb32b417c5bbb861e4b1a95f5f4ffeeb64d1dcbb49f40e531f456973084
```

密码经环境变量传给签名工具，不写入脚本参数或日志；`-Release` 禁止回退到自动生成的本地调试密钥。GitHub Secrets 的配置方式参考 [官方文档](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets)。
