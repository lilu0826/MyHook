# 丰巢可见广告与 SDK 屏蔽分析

分析样本：当前 `base.apk`，丰巢 6.45.0。目标：优先隐藏可见广告，并评估阻止 SDK 加载/展示的路径。

本文前半部分记录最初静态分析，末尾记录 MyHook 0.2.0 实机更新。静态定位的可见广告控件并未全部加入模块；已加入的 SDK 规则与验证边界见末尾说明。

## 已定位的可见广告

以下路径均相对于 `analysis/resources/resources/res/layout/`。

| 广告位置 | 样本证据 | 可采用的处理方式 | 仍需确认 |
| --- | --- | --- | --- |
| 首页图片弹窗 | `dialog_home_advert.xml`：`iv_ad_image` + `iv_click_cancel`，图片比例 3:4 | 按布局识别该弹窗，调用实际关闭流程；最终可定位业务展示方法进行阻断 | Dialog 具体类名、展示时机及关闭回调 |
| 插屏广告弹窗 | `dialog_interstitial_ad.xml`：`ll_interstitial_ad` + `iv_close` | 识别整个广告 Dialog 并关闭，不能仅把里面的图片隐藏 | 是否由 Dialog/DialogFragment 或其他窗口承载 |
| 统一支付成功页广告 | `activity_unipay_success.xml:55`、`activity_unity_pay_success.xml:64` | 仅隐藏其中的 `UnityPaymentAdvertLayout` | 是否被异步数据更新重新设为可见；是否保留空隙 |

## 优先入口：UnityPaymentAdvertLayout

XML 中直接写出了完整类名：

```text
kt.com.fcbox.hiveconsumer.app.business.payment.paysuccess.UnityPaymentAdvertLayout
```

三个位置共用此控件：

- `activity_unipay_success` 中的 `llPaySuccessAdvert`。
- `activity_unity_pay_success` 中的 `ll_pay_success_advert`。
- `dialog_interstitial_ad` 中的 `ll_interstitial_ad`。

它的内部模板 `unity_payment_advert_layout.xml` 是 `<merge>`，包含 `FCVideoPlayer`、`ImageView`、`FrameLayout`。这些是图片、视频和动态内容的容器线索，不能仅凭布局确定使用了哪个 SDK。

优先方案：在对应布局完成加载后识别这个具体控件，设置 `View.GONE`；如果后续异步回调重新展示它，再对已识别实例的可见性更新做针对性处理。GONE 会让控件不参与常规布局占位，具体约束、父容器留白仍需检查。[Android View 文档](https://developer.android.com/reference/android/view/View#GONE)

支付成功页同时包含金额、支付方式和查看订单按钮。只隐藏广告控件，不能把整个 Activity 当成广告跳过。插屏则应处理外层窗口：仅隐藏 `ll_interstitial_ad` 可能留下空白蒙层和触摸拦截。

## 首页弹窗的识别方案

建议增加一个独立的 `AdUiHooks`，让 MyHook 的入口负责安装，避免把所有规则挤入现有开屏逻辑。

1. 在 `LayoutInflater.inflate(int, ViewGroup, boolean)` 获取布局资源名称，只观察已确认的目标布局。
2. 保留原始 inflate 返回值及 attachToRoot 语义，标记实际生成的广告根节点。`attachToRoot=true` 时返回值可能是父容器，不能直接隐藏返回值；`<merge>` 也要单独处理。
3. 通过 Dialog 的内容视图定位标记，记录具体 Dialog 类名及页面，不记录订单、图片 URL 或其他业务数据。
4. 使用广告的关闭控件或确认过的业务关闭方法。需要核实关闭按钮是否还有持久化状态或清理监听器的行为，不能把 `dismiss()` 与正常关闭一概等同。
5. 若先让 Dialog.show 执行再关闭，仍可能闪现；要做到无闪现，需定位业务展示入口并确认跳过后的回调行为。

Android 的 Dialog 有独立的 show、cancel、dismiss 等生命周期，不能通过隐藏一个 ImageView 代替关闭整个窗口。[Dialog 文档](https://developer.android.com/reference/android/app/Dialog) 布局加载的返回及挂载语义见 [LayoutInflater 文档](https://developer.android.com/reference/android/view/LayoutInflater)。

本样本中 `iv_ad_image` 还出现在 `dialog_post_sale.xml`，所以不能仅凭这个 ID 判断“首页广告弹窗”。`imageView`、`fl_container`、`iv_close` 也是通用 ID；判断应结合布局名称、控件组合和所在页面。

## SDK 可以屏蔽到什么程度

需要区分三种目标：

| 目标 | 可行拦截位置 | 能做到什么 | 不能据此承诺什么 |
| --- | --- | --- | --- |
| 不显示 | 业务展示入口、广告控件、专用 Dialog 或 SDK 展示调用 | 广告不占据界面 | 不等于没有请求或预加载 |
| 不加载广告 | 业务广告请求封装或 SDK 广告位的加载入口 | 可阻止对应广告加载流程 | 不等于 SDK 完全不初始化、不联网 |
| 禁用 SDK 初始化 | 确认过的初始化入口/自动初始化组件 | 可能阻止更大部分 SDK 行为 | 需处理所有入口、回调与依赖，不能只凭包名前缀判定成功 |

本 APK 的 Manifest 可确认这些集成线索：

| 组件包/标记 | 具体证据 | Manifest 行 |
| --- | --- | --- |
| `com.bytedance.sdk.openadsdk` | `TTFileProvider`、`TTFullScreenVideoActivity` | 1309、1753 |
| `com.baidu.mobads.sdk.api` | `BdFileProvider` | 1317 |
| `com.qq.e.comm` | `GDTFileProvider` | 1321 |
| `com.sigmob.sdk` | `SigmobFileProvider`、广告 Activity | 1325、1617 |
| `com.huawei.openalliance.ad` | PPS 组件，ads-banner/ads-splash 元数据 | 1351、1357、1441 |
| `com.anythink` | `ATInitializationProvider`、广告容器 Activity | 1479、1481 |
| `com.windmill.sdk` | 多个 `InterstitialView_*` | 1631–1639 |
| `com.kwad.sdk` | 全屏、广告 WebView、广告文件 Provider | 1997、1999、2113 |

这些证明组件已打包或注册，不证明它们当前全部运行，也不是完整 SDK 清单。`FileProvider` 通常是文件访问组件，屏蔽它不等于屏蔽广告请求。`ATInitializationProvider` 则提示可能存在自动初始化入口，不能只看 Activity 启动后的一次初始化调用。

可以优先调查业务广告封装以及聚合层。ToBid 的官方 Android 文档展示了初始化回调、广告 load、ready 和 show 等不同阶段，还存在自动预加载；因此只拦截一次手动 load 或仅让 isReady 返回 false，都不能保证广告彻底停止。[初始化文档](https://doc.sigmob.com/tobid/2111/) [自动加载文档](https://doc.sigmob.com/tobid/24b/)

### 对当前加固样本的实施顺序

1. 先在广告页面真正出现时记录 Activity、Dialog、布局名称和真实 ClassLoader，确认用户看到的广告归属。
2. 从已确认的 `UnityPaymentAdvertLayout` 的运行时方法和调用链开始，找业务层的广告加载/展示入口。该类的方法体当前无法静态读取，不能杜撰一个方法名直接 Hook。
3. 再定位实际命中的 SDK/聚合适配器，核对其运行时方法签名和监听器接口。文档只能作为搜索线索，不代表 APK 使用相同版本。
4. 根据实际调用方处理“未加载/不可用”的分支；如果需要回调，应使用已核实的失败或关闭语义，并观察是否会触发另一家广告源或无限重试。不伪造广告加载/展示成功。
5. 分别验证冷启动、回前台、首页刷新、弹窗关闭、支付结果与查看订单。是否停止网络请求要另做网络观察，单看 UI 或一条 Hook 日志不够。

全局禁止类加载、禁止所有 WebView、把所有含 `ad` 的方法置空，都无法准确限定广告范围。对于当前“先隐藏可见广告”的目标，精确隐藏业务控件和关闭专用广告窗口更容易验证。

## App 自带的广告开关线索

`AndroidManifest.xml:499` 注册了 `kt.com.fcbox.hiveconsumer.app.business.setting.ad.AdSettingActivity`。

`activity_ad_setting.xml` 中包含：

- `sw_advert`，标签“广告展示”；提示资源 `text_recommend_advert_hint` 的内容是“开启后，将向您展示更多的广告”。
- `swShake`，标签“开屏 摇一摇 广告”。

这说明 APK 有相关设置 UI，但尚未确认当前界面是否开放入口、开关存储位置及具体控制范围。关闭它不应直接被描述为“禁用全部 SDK”。如果能在正常设置页找到它，可以先观察其对广告的影响。

## 当前结论

以上是最初静态分析的结论：可定位组件和控件，但不能仅凭 Manifest 给出已验证的 SDK 禁用规则。后续用户明确优先处理 SDK，新增实机工作如下。
